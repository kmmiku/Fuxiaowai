# Service operation

## Admin console incremental release — 2026-11-14

`server.js` calls `createAdminConsole(...).observe/handle` before the legacy routes. UI files are dashboard.html, admin.js, admin.css; the existing `/img/icon.png` is the logo. All additional assets/APIs require existing administrator Basic Auth. Public share/feedback contracts and existing ticket files are unchanged. Production received only this extension and UI; it did not receive unrelated workspace hardening. See ../docs/admin-console-20261114.md for verified deployment evidence.

Management writes reject cross-site Origin and scheme mismatches. The canonical public origin defaults to `https://fuxiaowai.xyz`; set `FXW_ADMIN_ORIGIN` when changing domain. Other direct hosts use the actual connection scheme. Do not infer proxy scheme from untrusted forwarded headers. Existing credentials are unchanged; no SSH credential is sent to the browser.

`ROOT/admin/audit.json` and `alerts.json` retain at most 2000 entries each / 30 days; API views show 200. They use private temporary files and atomic rename, serialized and coalesced by 100ms. Write failures retry every5s and surface storageError. If an existing history file cannot be parsed/read, its writes are blocked to prevent overwrite; stop service, preserve that file, restore a verified good copy from backup (or deliberately archive and replace the damaged file), then restart. No browser button clears audit history. These are single-process records, not tamper-proof compliance logs; forced termination may lose unflushed records.

Probes run every15s, canonical HTTPS health/certificate every60s. CPU/memory/disk≥90% for three successive samples warn; ≥3 HTTP5xx/min or ≥10 failed supplied Basic credentials/5min warn; absent authorization first challenges are not counted. Certificate warning starts below14 days. Restarted alerts are marked interrupted until freshly re-evaluated. Historical CPU/network trends and external notification delivery are not included.

`tools/deploy-admin-console.py` is an on-VPS, source-hash-guarded release script, not a local dry run. It stops the service, creates an encrypted data backup with a root-only local key, preserves source, patches only the verified deployed version, clears feedback with explicit authorization, restarts and compares every original ticket SHA256. Failure restores source/feedback; ticket files are never overwritten. Preserve the root-only backup/key together in protected storage; remove backups within30 days according to retention policy. Never print or commit the key or manifest of real codes.

No deployment is performed by repository changes. Review these examples on the target host. Use Node 22 or newer. Create `/etc/fxw-share.env` from the example, replace both credential placeholders, and manually run `bash deploy.sh` from this directory. Configure nginx with a real HTTPS certificate; its sample is an HTTPS server snippet. The service binds to loopback 8080 and runs as `fxw`, with data in `/var/lib/fxw`. Never commit the actual environment file.

`FXW_TRUST_PROXY=1` trusts the single `X-FXW-Client-IP` address only from loopback sockets. nginx overwrites it using the socket peer. Other forwarded headers are ignored. Restrict local machine access: local processes can impersonate the proxy. Disable this setting for direct connections.

Per minute defaults: 1200 API requests per IP, 120 new shares per IP / 600 globally, 20 feedback per IP / 100 globally. Shared school NATs can submit multiple reports. Feedback 429 responses include `Retry-After: 60` and `retryAfter: 60`. Counters are bounded, in memory and reset on restart. Storage count quotas are approximate during concurrent writes and the 30-second statistics refresh; disk water checks cache for five seconds. Reserve 512 MiB by default. Monitor available disk and tune quotas for your host. Run one process: limits are not distributed across replicas.

At most eight body-bearing writes are admitted together across share creation, feedback submission and admin feedback marking. `FXW_MAX_ACTIVE_WRITES` tunes this shared limit (1–32); the default keeps eight 4 MiB feedback buffers plus parsing/image overhead within a small service memory budget. Saturation returns HTTP 503 with `Retry-After: 5` and `retryAfter: 5` before buffering the body. Slots release on completed responses and disconnected clients. Health checks and read routes remain available. Share/admin bodies are limited to 64 KiB; feedback bodies to 4 MiB. Request timeout is 30 seconds. Keep nginx request-body limits and service memory limits aligned; do not raise concurrency without measuring peak memory.

Existing JSON files remain readable. New data uses private temporary files followed by atomic rename, preventing partially visible JSON; this does not guarantee survival of power loss. Optional `X-FXW-Request-ID` (8–128 letters, digits, `_` or `-`) coalesces feedback retries by IP for 24 hours. A SHA-256 key is stored with the feedback and rebuilt on restart; the raw request ID is not stored. Old clients need no header. An IP change may allow duplicate submissions. Use a fresh ID for every new report. Failed submissions can be retried with a new ID. Screenshots must be under 1.5 MiB each, and the complete JSON body under 4 MiB.

Retention runs on startup and hourly: shares 30 days; feedback and attached images 365 days from creation, including unread records. Expired shares are also rejected on reads. Orphan images expire after 365 days by file timestamp. Existing timestamps are respected. There is no public share withdrawal API; administrators can delete shares and feedback with attachments in the dashboard.

Configure host logging: journald `MaxRetentionSec=30day` plus suitable `SystemMaxUse`, and nginx logrotate retention no longer than 30 days. Verify host settings before promising log deletion. Service events include IDs and IP addresses; never add bodies, passwords or screenshots to logs. Encrypt backups, restrict access and expire them within 30 days (or erase affected records from backups on deletion requests).

Backup: stop `fxw-share`, archive `/var/lib/fxw` to an encrypted backup destination, then restart. Save the environment separately in the secret store. Restore: stop the service, unpack a verified archive into `/var/lib/fxw`, restore ownership `fxw:fxw` and private permissions, start, then check `/healthz`, authenticated stats and an existing share. Startup cleanup removes expired records. Before upgrades preserve deployed source; roll back by stopping, restoring the source copy and starting against the unchanged JSON directory.

Local verification from repository root: `node --test tests/server-http.cjs`. Tests use only loopback HTTP and temporary data; they never contact production.
